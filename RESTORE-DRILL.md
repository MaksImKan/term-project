# Restore drill — протокол

Бекап, який ніхто не відновлював, це не бекап, а файл. Нижче — результати
реальних прогонів `scripts/restore-drill.sh`: скрипт піднімає **чистий** Postgres
на порожньому томі, відновлює туди найсвіжіший дамп і порівнює контрольне
значення з тим, що було знято **на момент дампу** (`count|sum` по `orders`,
записане `backup.sh` у файл `*.checksum`).

Відтворити:

```bash
bash scripts/with-secrets.sh dev bash scripts/backup.sh
bash scripts/with-secrets.sh dev bash scripts/restore-drill.sh     # друкує MATCH
```

## Прогони

| | Прогін A — обсяг сіду | Прогін B — реалістичний обсяг |
| --- | --- | --- |
| Дата | 2026-10-01 18:28 UTC | 2026-10-01 18:29 UTC |
| Що в базі | `npm run seed`: 6 users, 10 products, 8 orders, 18 items | `db/seed.sql`: 50k users, 120k products, 200k orders, 400k items |
| Розмір дампу (`pg_dump -Fc`) | **40 KB** (37 523 Б) | **12 MB** (12 363 108 Б) |
| Час `pg_dump` | < 1 с | **3 с** |
| Час `pg_restore` | **107 мс** | **5 374 мс** |
| **RTO (увесь drill)** | **1,3 с** (1 276 мс) | **6,8 с** (6 750 мс) |
| Контрольне значення до/після | `18\|11896200` → `18\|11896200` | `200000\|751255909940` → `200000\|751255909940` |
| Результат | `MATCH` | `MATCH` |

«RTO (увесь drill)» — це час від старту чистого Postgres до підтвердженого
`MATCH`: підняття порожнього інстансу, створення бази, `pg_restore`, зняття
контрольного значення і порівняння. Саме це число має сенс порівнювати з
цільовим RTO, бо воно включає все, що справді треба зробити.

Стенд: Postgres 16.13, 2 vCPU, дані і дамп на тому самому диску. На вашій
машині числа будуть іншими, порядок величини — тим самим.

## RTO

**Виміряний технічний RTO: 1,3 с на обсязі сіду, 6,8 с на 200 тис. замовлень.**

Це нижня межа — скільки коштує саме відновлення. Чесний операційний RTO для
інциденту «база втрачена» складається ще з трьох доданків, які drill не міряє:

| Етап | Оцінка |
| --- | --- |
| Помітити проблему (alert → людина) | 5–15 хв (без моніторингу — до годин; це робота ДЗ-29) |
| Рішення «відновлюємося з бекапа» + підготовка інстансу | 5–10 хв |
| Власне відновлення (виміряно) | **7 с** на поточному обсязі |
| Переключити застосунок (рядок підключення у сховищі, рестарт) | 2–5 хв |
| **Операційний RTO, оцінка** | **15–30 хв** |

Відновлення — найдешевша частина. Дорого коштує все, що навколо, і саме тому
drill має сенс: він прибирає єдину складову, яку неможливо оцінити без практики —
«а чи взагалі відновиться».

Як RTO зростатиме: `pg_restore` масштабується приблизно лінійно за обсягом
(40 KB → 107 мс, 12 MB → 5,4 с, тобто ≈ 0,45 с на мегабайт стисненого дампу).
На 10 ГБ дампа це вже години, і тоді відповідь не «швидший диск», а інша
стратегія: фізичний бекап (`pg_basebackup`) + PITR або гаряча реплика, з якої
роблять promote за секунди.

## RPO

**RPO = 24 години** (точніше — до 23 год 59 хв).

Чому саме стільки: розклад у `backup.cron` — `17 3 * * *`, тобто один повний дамп
щоночі о 03:17. Якщо база згине о 03:16, втрачається все, що записано з 03:17
попередньої доби. WAL-архівування не налаштоване, тож між дампами точки
відновлення немає взагалі.

Для цього проєкту така цифра приймається свідомо: це навчальний маркетплейс без
реальних грошей. Для системи, яка приймає платежі, 24 години втрат — неприйнятно,
і шлях зменшення відомий і вимірюваний:

| Налаштування | RPO | Ціна |
| --- | --- | --- |
| Нічний `pg_dump` (зараз) | **24 год** | нуль |
| `pg_dump` щогодини | 1 год | дешево, але дамп блокує ресурси й росте разом із базою |
| WAL-архівування + PITR | **1–5 хв** (розмір `archive_timeout`) | окреме сховище WAL, складніша процедура відновлення |
| Streaming-реплика (async) | **секунди** | ще один інстанс Postgres, лаг реплікації |
| Synchronous replication | **0** | кожен COMMIT чекає на реплику — платимо латентністю запису |

Наступний крок для цього проєкту — винести дампи з локальної теки в S3 (ДЗ-26):
зараз і база, і бекап живуть на одному диску, тож «диск помер» забирає обидва.
Це найслабше місце поточної схеми, і воно слабше за будь-яке RPO в таблиці вище.

## Що drill перевіряє, а що ні

Перевіряє:

* дамп читається і `pg_restore` проходить без помилок у **чисту** базу
  (`--no-owner --no-acl`: ролі `marketplace` у чистому контейнері немає);
* дані на місці — `count` і `sum` по ключовій таблиці збігаються з моментом дампу;
* процедура відтворювана: повторний запуск створює новий том і теж дає `MATCH`,
  бо кожен прогін починається з порожнього тому (відновлення у непорожній том —
  головна причина фальшивих `duplicate key`).

Не перевіряє (і це варто знати):

* консистентність **між** дампом і зовнішніми системами — черга `tasks`
  відновиться в стан на момент дампу, і задачі, вже відправлені в реальність,
  виконаються вдруге;
* що бекап існує за межами цієї машини (поки що не існує — див. S3 вище);
* що відновлена база витримає навантаження: drill міряє `pg_restore`, а не те,
  що буде після `ANALYZE` (статистику дамп не містить).
